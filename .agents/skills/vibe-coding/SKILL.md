# Vibe Coding

先理解目标，再制定最小计划，随后自主执行并用证据验证。以正确性和安全性为前提减少无效读取、重复说明和 Token 消耗。

## 优先级

1. 正确性与数据安全
2. 用户意图与任务完成度
3. 工作区和架构安全
4. 可验证性
5. Token 与执行效率

## 选择工作模式

使用快速模式处理单行修改、微小调整和简单说明：检查直接依赖后执行定向验证。

使用规划模式处理新功能、Bug、重构、删除、多文件修改和高风险操作：

1. 明确目标、限制和可验证的成功标准。
2. 调查相关文件、调用方、数据和潜在副作用。
3. 制定最小步骤、风险和验证方法。
4. 计划明确后直接执行，不为普通安全步骤等待用户确认。

仅在选择会实质改变结果、操作不可逆、需要新权限、会影响外部系统，或需求存在关键歧义时请求用户决定。

## 执行工作流

1. **建立基线**：检查工作区状态、已有修改、相关测试和已知失败。区分用户改动与当前任务改动。
2. **确定方案**：优先复用可靠组件；避免无关重写，但不要用低价值兼容层维持错误架构。
3. **分片实现**：一次完成一个可验证的逻辑切片。仅并行处理边界独立的工作。
4. **逐步验证**：每个切片完成后运行最小相关检查；失败时先定位原因再继续。
5. **最终验证**：执行与风险相称的编译、测试、引用检查和差异审计。
6. **交付结果**：先说明实际结果，再列验证证据、已知限制和下一步。

## 决定升级或替换

- 当现有代码职责清楚、数据结构可扩展且修改风险可控时，直接升级。
- 当固定假设阻碍目标、兼容层会长期污染架构，或旧功能事实上未被使用时，调查引用后使用新系统替换。
- 始终保护有价值的用户数据、存档和未提交工作；必要时提供迁移，而不是机械保留旧实现。
- 用户明确允许或禁止兼容时，以用户决定为准。
- 删除代码或资产前，检查调用方、序列化引用、场景、Prefab、资源 GUID 和存档影响。

## 自验证

在修改前记录基线，避免把原有失败误判为新回归。根据风险选择验证强度：

- **低风险**：执行语法、格式、定向搜索或最小测试。
- **中风险**：执行相关模块编译、定向测试和 `git diff` 审计。
- **高风险**：执行完整编译、相关测试套件、数据迁移、场景/资源引用和失败路径验证。

验证时遵守以下规则：

- 不用陈旧日志或旧测试结果证明当前代码成功。
- 测试失败后判断是基线问题、环境问题还是本次回归；不得忽略新回归。
- 工具挂起或相同错误重复出现时，停止盲目重试，检查进程和日志并更换方法。
- 只终止由当前任务启动且确认挂起的进程；不得通过删除用户文件或重置工作区来“修复”验证。
- 最终检查 `git status`、`git diff --check`、临时产物和无关改动。
- 报告实际执行的测试名称、通过数量和未验证部分；没有证据时不得声称完成。

## 使用 Subagent

不要强制为每个任务使用 Subagent。仅当系统允许且同时满足以下条件时使用：

- 子任务具体、有边界并可独立完成。
- 并行收益明显高于沟通与合并成本。
- 子任务不依赖尚未产生的前置结果。
- 写入文件不重叠，或子任务仅进行只读研究与独立验证。

不要为单文件小改动、强顺序任务、共享场景文件或主 Agent 能快速完成的工作启动 Subagent。

给每个 Subagent 提供任务合同：

- 目标和成功标准
- 必要输入和允许读取范围
- 允许修改的文件或明确只读
- 禁止触碰的用户改动
- 预期交付物和验证命令

共享工作区中禁止多个 Agent 同时修改重叠文件。主 Agent 负责读取返回结果、检查实际差异、解决冲突并重新运行最终验证；不得仅凭 Subagent 声称成功就交付。

使用 Subagent 前向测试 Skill 时，提供原始任务和最少必要上下文，不泄露预期答案或已有结论；由主 Agent 比较真实产物和失败模式。

## Git 检查点

本项目每完成并验证一个逻辑切片后创建独立 Git commit：

- 提交前检查 `git status`、实际差异和验证结果。
- 使用精确路径只暂存当前切片的文件，不夹带用户原有修改、无关变更、日志或临时产物。
- 使用简洁且能说明结果的提交信息；不要提交失败、未验证或只完成一半的切片。
- 当前切片与用户修改重叠且无法安全分离时，停止提交并请求用户决定，不得重置或覆盖工作区。
- 除非用户明确要求，不执行 push、rebase、amend、发布或创建 PR。

## Unity 与游戏项目检查

处理 Unity 项目时按改动风险检查：

- Unity 编译、相关 EditMode/PlayMode 测试和构建目标兼容性
- Scene、Prefab、Missing Script、序列化字段、GUID 与 `.meta`
- Addressables、下载内容、持久化路径和移动端包体边界
- 存档版本、云端冲突和旧数据迁移或明确退役策略
- 未提交 Scene、ProjectSettings 和用户资产不被覆盖

面向玩家的功能只有同时考虑逻辑、动画、点击/状态音效、可选震动、本地化、错误反馈、存档和相应测试时才算完成。后台基础设施可以分阶段交付，但不得把缺少表现层的功能描述为完整游戏体验。

## 处理“继续”

当用户说“继续”“continue”或“do all”时：

1. 确认并补完当前阶段。
2. 验证通过后更新计划状态。
3. 简短说明下一阶段并直接开发，除非遇到需要用户决定的真实阻塞。
4. 按 Git 检查点提交已验证切片；仅在用户明确要求时推送或执行外部发布操作。

## 沟通与完成条件

保持进度更新简短且有信息量；长任务持续提供状态，不重复完整计划。最终答复必须自包含。

只有在成功标准已满足、风险相称的验证已通过、无未说明的新回归、无意外文件修改，且已清楚报告限制时，才声明任务完成。
